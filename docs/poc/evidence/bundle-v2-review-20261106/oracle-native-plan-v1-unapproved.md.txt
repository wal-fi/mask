## 1. Objetivo e fronteira

Uma prova nativa única do caminho W1 real: controlador PID1 e worker Linux do
pacote **instalado** na candidata aceita, contra PostgreSQL16 próprio,
descartável e isolado, com dados sintéticos. Fecha, se verde, a etapa3 do
WORKER-SESSION-PLAN e fornece evidência para B-1 fim a fim no perfil local.

Não é: coordenador Windows simulado novo; ingresso PGWire/MCP/Admin/IDE; SQL
liberada (continua0A000); perfil C1 pronto ou injetado em domain.py; B-2
estrito ou produção; pressão/concorrência/cliente lento/gerações. Não depende
do laboratório Windows PG16 shell e não alega Native3s verde: aquele gate
continua NOT_MEASURED, evidência congelada, sem dispensa. Source20/estado16 e
a tentativa3f12dc584c29 (FAILED_ONLY_OPERATOR_ABORT) permanecem fixos.

## 3. Restrições impostas pelo código atual (não contornar)

Lidas em worker_session.py/worker_process.py/worker_protocol.py/worker_job.py/
linux_guard.py:

- WorkerSession exige Linux, GuardFacts CONTROLLER com `pid==getpid()==1`,
  dumpable0, core(0,0), PDEATHSIG0. Logo o controlador é **o PID1 do

- protect_process exige UID/GID10001, capabilities0, NNP1, Seccomp2 e
  **Threads1** no momento do guard; VmSize+8MiB < AS; AS só diminui.
- Worker lançado por `sys.executable -I -B -m maskgw.runtime.worker_process
  FD PPID AS IDLE`, env fixo `child_environment`, stdout/stderr DEVNULL,
  stdin PIPE vazio até GUARD_READY. Filho herda o AS hard do pai e o reduz:
  AS_filho ≤ AS_controlador.
- Owner de lifetime é a thread que chamou open (não daemon, nunca pool);
  `_exclusive` recusa outra thread. Uma operação por vez; `send_result_to`
  só em RESULT, após DONE correlacionado.
- Deadlines: abertura12s desde antes de Popen; job `statement_timeout_ms+10s`
  sem renovação; envio30s; limpeza3s; reap3×0,25s após kill.
- Imports do worker ocorrem antes do guard e devem continuar sem segredo.

## 4. Topologia

```text
Windows host (programa host novo, bounded CLI)
 ├─ rede Docker própria --internal, label/task exclusivos, sem portas no host
 │   ├─ PG16 próprio (fora do domínio do gateway, servidor upstream explícito)
 │   └─ container gateway na candidata 621cc7f7
 │        PID1 = controlador lab (pacote instalado + guard CONTROLLER)
```

## 5. Segredos

Gerados pelo host em memória, aleatórios por rodada: senha superuser do PG,
senha do papel read-only, chave HMAC sintética. Nenhum em argv/env do gateway,
imagem, arquivo, log ou evidência.

- PG create recebe a senha superuser só pelo ambiente do processo CLI
  (`-e NOME` sem valor), como D-117. Fixture e senha do papel read-only
  entram no psql **por stdin** dentro do container PG, nunca argv.
- Controlador recebe um único frame limitado por stdin **depois** de emitir
  sua linha pública GUARD (fatos escalares, sem segredo). Frame contém
  conninfo fixado, senha read-only, chave HMAC, expectativas por caso
  (digests dos corpos D-113 esperados e canários brutos a procurar). EOF
  exigido após o frame. Proposta a revisar: o mecanismo exato depende de
  como `docker run -i` sem TTY entrega stdin ao PID1 (Q3).
- Toda saída/artefato é varrida pelos três segredos e pelos canários
  brutos; qualquer ocorrência reprova, mesmo se redigida.

## 6. Papel e dados no PG

Fixture pinada por hash, aplicada uma vez pelo superuser via psql/stdin:
schema sintético, tabelas com colunas ALLOW/MASK/EXCEPTION, valores canário
aleatórios gerados pelo host; papel com somente CONNECT/USAGE/SELECT, sem
ownership/escrita/execução de função de usuário/bypass de RLS,
`default_transaction_read_only=on`, statement_timeout fixado (SPEC§4.3).
Isso é preparação do servidor descartável, não SQL do gateway.

## 7. Perfis e custos

Gateway container: UID/GID10001, rootfs RO, cap-drop ALL, NNP, seccomp
padrão, memory512MiB, swap0, pids32, CPU1, nofile128, core0, tmpfs/tmp16MiB,
shm8MiB, rede própria interna. Iguais aos fatos D-120 já medidos; só a rede
muda de none para a interna própria.

- Controlador AS384MiB; WorkerProfile.address_bytes256MiB. Justificativa:
  filho importa ≈91MB VmSize (D-120) +8MiB de margem, sobra para libpq,
  resultado materializado, encode 2F+scratch; maior VmPeak Linux registrado
  com carga de imports foi154MB (LOADED-RUN, Debian, não Oracle). 256≤384
  satisfaz a herança. Não são calibração de capacidade.
- ResultLimits: max_frame_bytes F=16MiB (teto D-113, sem novo limite);
  max_rows igual ao da geração sintética.
- Ledger D-112: W≥256MiB por worker (D-116: W≥cota imposta); P≥2F+overhead
  (D-114); valores exatos fixados no estado preparado antes de efeitos.
- AS é espaço virtual, distinto de memória cobrada. Soma AS (640MiB) excede
  memory.max512MiB de propósito declarado: o cgroup pode agir antes do AS,
  sob a semântica documentada D-119, sem limite numérico inventado. Nenhuma
  alegação STRICT, de B-2 ou de produção. OOM/MEMORY é FAIL registrado;
  nenhum limite aumentado durante ou após a rodada para obter verde.
- PG container: 512MiB/swap/pids256/CPU1 (perfil D-117), fora do domínio.
- Sem pressão/carga até perfil definido e código/guards revisados.

## 8. Matriz de aceitação (finita, cada caso uma vez, sem retry)

Admissão (antes de B, qualquer falha aborta sem B):
- A1 imagem local com ID exato 621cc7f7; Config/labels conformes; atestação
  instalada e manifesto recalculados iguais a f0c3cd54/d4d4b29b; fontes124
  sem diferença; PG16 image ID local registrado, sem pull.
- A2 idade monotônica **incluindo suspensão** e identidade de boot iguais
  entre A/Observe/Ready/B, impostas em código; vencida/alterada aborta.
- A3 inventário Docker inicial sem recursos com o label/task da rodada.

Controlador/worker:
- N1 módulos `maskgw.*` importados com `__file__` sob o site-packages da
  venv instalada; nenhum caminho do payload lab no sys.path de maskgw.
- N2 guard CONTROLLER antes de qualquer leitura do stdin; Threads1 no guard.

Sessão1 persistente (um worker, uma conexão, jobs1..12 sequenciais):
- S1 open: GUARD_READY igual a PID/PPID/AS; OPENED HMAC conferido; baseline
  S1 com readonly on, UTF8, row_security on.
- S2 SELECT ALLOW: corpo igual ao digest esperado; frame+DONE antes de envio.
- S3 MASK/HMAC: coluna anunciada text25; digest esperado; canário ausente.
- S4 derivados: alias, expressão, UNION, CTE, subquery, todos mascarados.
- S5 exception pelo nome autoritativo.
- S6 truncamento max_rows: rows=max_rows.
- S7 maior frame sintético declarado no estado (≤F, bytes exatos prévios).
- S8 frame acima de F → LIMIT recuperável; S9 SELECT seguinte correto.
- S10 escrita/função perigosa → QUERY recuperável, sem efeito no PG.
- S11 timeout (mesma forma do caso D-117) → TIMEOUT recuperável; S12 seguinte
  correto e saúde/S1 iguais.
- Todo resultado entregue por `send_result_to` a um sink local (Q4); nenhum
  conteúdo de célula, SQL ou frame sai do controlador, só booleanos/contagens/
  categorias fechadas.
- Fim: CLOSE gracioso, reap real, release RELEASED.

Sessões terminais (cada uma com worker novo, exatamente uma vez):
- T1 TYPE (OID fora da tabela) recuperável e consulta seguinte, depois CLOSE.
- T2 término do próprio backend pelo superuser → CONNECTION fatal, kill/reap.
- T3 blackhole: `docker pause` do PG próprio durante job → deadline do pai,
  kill/reap; PG despausado só para limpeza.
- T4 EOF: controlador fecha seu socket → filho termina; reap.
- T5 idle do filho vence → fim; reap.
- T6 request_stop durante job → kill/reap, sem frame exposto.
- T7 morte do PID1: host mata o container gateway com worker vivo; inspect
  confirma término de todo o namespace; PG mostra zero backends do papel
  dentro de janela finita (reap local não prova fim instantâneo upstream).

Para cada fatal: nenhum frame/saída bruta, nenhum envio, HELD/RELEASED
conforme fatos reais; erro do SO retém capacidade, nunca "limpo" por timeout.
Total: 1 sessão persistente com12 jobs + 7 terminais; nenhuma repetição.

Saída pública do controlador: linhas JSON fechadas e limitadas (tamanho total
pré-declarado), sem valores. Host persiste a linha HELD/validada quando houver
(lacuna Q1 da LOADED-RUN).
