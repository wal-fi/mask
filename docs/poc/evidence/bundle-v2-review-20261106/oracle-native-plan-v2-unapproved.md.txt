## 1. Objetivo e fronteira

Uma prova nativa única do caminho W1 real: controlador PID1 e worker Linux do
pacote **instalado** na candidata aceita, contra PostgreSQL16 próprio,
descartável e isolado, com dados sintéticos. Se verde, fecha a etapa3 do
WORKER-SESSION-PLAN e fornece evidência para B-1 fim a fim no perfil local.

Não é: coordenador Windows simulado novo; ingresso PGWire/MCP/Admin/IDE; SQL
liberada (continua0A000); perfil C1 pronto ou injetado em domain.py; B-2
estrito ou produção; pressão/concorrência/cliente lento/gerações. Independe
do laboratório Windows PG16 shell e não alega Native3s verde (continua
NOT_MEASURED, evidência congelada, sem dispensa). Source20/estado16 e a
tentativa3f12dc584c29 (FAILED_ONLY_OPERATOR_ABORT) permanecem fixos.

## 3. Restrições do código atual (não contornar)

Lidas em worker_session/worker_process/worker_protocol/worker_job/linux_guard:

- WorkerSession exige Linux e GuardFacts CONTROLLER com `pid==getpid()==1`,
  dumpable0, core(0,0), PDEATHSIG0: controlador é **o PID1 do container**.
- protect_process exige UID/GID10001, caps0, NNP1, Seccomp2 e **Threads1 no
  instante do guard**; VmSize+8MiB<AS; AS só diminui. Threads adicionais só
  podem nascer depois do guard.
- `open/query/send_result_to/close` passam por `_exclusive`: só a thread que
  chamou open (não daemon). Essa é a thread principal, dona de todo o
  lifetime e criadora do filho (PDEATHSIG). `request_stop` é o único método
  documentado como cross-thread.
- Worker: `sys.executable -I -B -m maskgw.runtime.worker_process FD PPID AS
  IDLE`, env fixo, stdout/stderr DEVNULL, stdin vazio até GUARD_READY; AS do
  filho ≤ AS do controlador. O filho conecta com `verify_capabilities=True`
  e S1 baseline: a verificação pós-conexão acontece **no worker**.
- Deadlines: abertura12s desde antes de Popen; job `statement_timeout_ms+10s`;
  envio30s; limpeza3s; reap3×0,25s após kill; send ao filho limitado por
  `idle_end`.

## 5. Segredos e a exceção do PG

Gerados pelo host em memória por rodada: senha superuser PG, senha do papel
read-only, chave HMAC sintética, canários brutos.

- **Exceção única do servidor próprio:** como D-117, a senha superuser vai
  só ao ambiente do processo Docker CLI de create (`-e NOME` sem valor) e,
  portanto, ao Config.Env do container PG próprio. O ambiente não é
  globalmente livre de segredo; mitigação: inspect com template que exclui
  Config.Env, container removido ao fim. Nunca se aplica a gateway, worker
  ou credencial de usuário.
- Fixture e senha read-only entram no psql do container PG por stdin.
- Gateway: nenhum segredo em argv/env/imagem/arquivo. Só no frame LAB_INIT
  pelo stdin, depois da linha GUARD (§9). Provider no controlador é
  `MappingSecretProvider` fechado com a chave HMAC; nenhuma releitura ou
  fallback de ambiente.
- Toda saída/artefato é varrida pelos segredos e canários; qualquer
  ocorrência reprova, mesmo redigida.

## 6. Snapshot: caminho de captura (F4) — B1 BLOCKED

Lido em runtime/snapshot.py, runtime/candidate.py e nos testes de snapshot.

- `build_candidate(capture_snapshot=True)` resolve o destino e depois chama
  sempre `verify(prepared)`. O default `verify_prepared` conecta no processo
  chamador, o que é I/O proibido no pai. Os testes usam
  `verifier=lambda _: None` e `resolver` fake: é **bypass de teste**, não
  caminho aceitável aqui.
- `capture_template(policy, config, conninfo, secrets)` é pública, mas o
  `GatewayConfig` efetivo vem de `_compile`, privado. Recompor esses passos
  no laboratório duplicaria o pipeline de compilação; recusado.
- **B1 BLOCKED — API necessária antes do código do controlador:** função
  pública estreita em candidate.py que reutilize exatamente `_compile` +
  `RecordingSecrets` + `build_conninfo` + `capture_template`, com
  `resolve_destination` real e `expected_addresses` = IP fixado, sem
  conectar nem verificar, documentando que a verificação D-071 ocorre no
  `connect()` do worker. Erros fechados `DatasourceCandidateError`. Requer
  desenho/revisão próprios; este plano não a cria.
- Decisão pendente dessa API: `resolve_destination` com resolver default
  usa um filho limitado (D-092) mesmo para IP literal. Esse processo extra
  conta em pids32 e precisa de reap comprovado no PID1. Ou a API aceita
  só IP literal validado por `_validate_address` sem filho. Escolha na
  revisão da API, não aqui.

## 7. Destino e TLS do laboratório (F7)

Lido em datasource/destination.py e datasource/models.py:

- `DestinationPolicy()` default (allow_public False, allow_loopback False,
  allowed_hosts vazio). `_validate_address` aceita `is_private` antes de
  exigir allowlist. IP RFC1918 da rede interna passa sem allowlist ou bypass.
  Loopback, link-local, metadata e multicast continuam recusados. Admissão
  exige que o IP lido seja privado; senão, aborta antes de B.
- `TlsSettings.mode="disable"`: perfil explícito de laboratório isolado
  (rede interna sem outros membros, sem portas). SCRAM não transmite a
  senha. **Não** é alegação de produção. `require`/`verify-full` com
  certificado próprio continua gate separado do upstream real.

## 9. Máquina de estados host↔controlador (F2)

Canal: stdin/stdout do PID1 via `docker run -i` sem TTY.

- Controlador→host: linhas JSON fechadas ASCII, ≤512bytes cada; total pelo
  estado (≤256 linhas). Escritor único: a thread principal.
- Host→controlador: frames binários com tamanho exato.
- Nenhum sleep de coordenação; toda espera tem prazo; nenhum retry.

Fases obrigatórias:

1. `GUARD` (C→H): emitida pela thread principal depois de protect_process
   CONTROLLER e antes de qualquer leitura do stdin. Campos: pid=1, AS,
   Threads1, dumpable0. Host confere.
2. `LAB_INIT` (H→C), **uma vez**, ≤64KiB: conninfo-parâmetros, senha
   read-only, chave HMAC, expectativas por job (comprimento e SHA-256 do
   corpo D-113 esperado, canários a procurar). Prazo10s.
3. `INIT_OK` (C→H) após o snapshot de G1/G2 (depende de B1) e o sink pronto.
4. Para cada caso, em ordem fixa (§11–§12), com seq monotônico:
   `READY{case,seq}` (C) → ação do host, se houver → `GO{case,seq}` (H) →
   execução → `RESULT{case,seq,campos fechados}` (C) → `ACK{case,seq}` (H).
   O caso T4 insere `ARMED` (C) e `STOP` (H) entre GO e RESULT.
5. `SUMMARY` (C) depois do último caso antes de T6; host não fecha o stdin
   (EOF) antes disso. Em T6 o host mata o container (§12).

Frames de controle (16bytes): magic, kind GO/STOP/ACK, case u16, seq u32.
Proibidos: SQL arbitrária, case fora da tabela, seq fora de ordem, frame
extra, EOF antecipado. Qualquer violação: controlador fecha a sessão ativa,
emite `ABORT{fase}` e sai 1; host vai para cleanup e marca FAILED. Casos não
alcançados ficam NOT_RUN, nunca repetidos.

## 10. Sink e saída (F8)

- Thread sink não daemon, criada depois do guard e antes do primeiro open.
  Lê o par interno de um `socketpair` em buffer fixo de64KiB. Atualiza
  SHA-256 e contagem; nunca guarda o corpo nem o publica. Compara com a
  expectativa do job (comprimento exato) e entrega à thread principal só
  booleano+contagem.
- A thread principal chama `send_result_to(RawChannel(par))`: o
  backpressure é o buffer do socket, limitado pelo prazo de envio de30s.
  BUSY/DEADLINE/ReceiverError → sessão fecha conforme D-114; pin incerto
  fica HELD e a capacidade fica retida, nunca é declarada limpa.
- Parada: depois do último job, a thread principal faz shutdown do seu par.
  O sink termina por EOF. join com prazo de3s; se falhar, evidência FAILED
  e capacidade retida (o processo termina em T6 de qualquer forma).
- Não há segundo executor de SQL, conexão no pai nem decoder de linhas.

## 12. Sessões terminais, ordem fixa, uma vez cada (F3)

- **T1 backend terminado** (G1): open → READY → host confirma por psql do
  superuser exatamente1 backend do papel read-only e o termina (1 linha
  true) → GO → controlador envia `SELECT 1` → esperado ERROR fatal
  CONNECTION ou INTERNAL, sessão fecha com kill/reap.
- **T2 blackhole** (G1): open → READY → host `docker pause` do PG por CID
  conferido → GO → `SELECT 1` → prazo do pai (11s) → JOB fatal, kill/reap →
  RESULT → host `docker unpause` do mesmo CID por identidade, inspect
  Running/Paused false e `pg_isready` dentro de janela finita → ACK.
  **Restauração faz parte do próprio T2.** Se o unpause ou o readiness
  falhar, nenhum caso posterior roda (NOT_RUN), host vai a cleanup e FAILED.
- **T3 idle do filho** (G1, idle_ms1000): open → READY → GO → espera local
  limitada (idle_ms+1s, prazo monotônico, não coordenação) → `SELECT 1` →
  send recusado pelo `idle_end` vencido → JOB fatal, reap. Limite: a API
  pública não expõe o returncode; não se alega distinguir saída por idle de
  kill.
- **T4 request_stop durante job** (G2): open → READY → GO → C emite `ARMED`,
  inicia a thread stop-watcher e chama `query("SELECT count(*) FROM
  generate_series(1,2000000000)")` → host consulta `pg_stat_activity` do
  papel até ver state active (≤20 chamadas psql sequenciais, sem sleep) →
  STOP → watcher chama só `session.request_stop()` e termina → principal
  recebe JOB fatal, kill/reap, join do watcher (3s) → RESULT. Sem active
  observado: o host não envia STOP, o job acaba por prazo, T4 FAIL.
- **T5 EOF do canal**: **UNRESOLVED/BLOCK_NATIVE**. Nenhuma API pública fecha
  só o socket do pai sem kill. `close()` envia CLOSE e reaps; mexer em
  `_sock` é proibido. O ramo EOF do filho (`_next` → None) é o mesmo de
  idle/TIMEOUT, já exercido em T3 e nos testes simulados D-121. Follow-up:
  decidir em revisão se T3 cobre o requisito ou se é preciso um método
  público revisado. Não roda até lá; fica NOT_RUN declarado.
- **T6 morte do PID1/namespace**: SUMMARY → open (G1) → READY → host `docker
  kill` do gateway por CID → inspect: Running false, Pid0, sem processos.
  PG mostra zero backends do papel em janela finita. Reap local não prova
  fim instantâneo upstream.

Em todo fatal: nenhum frame ou saída bruta, nada enviado, HELD/RELEASED
conforme fatos reais. Erro do SO retém capacidade, nunca "limpo" por prazo.
Total: 7 sessões (P + T1–T4 + T6), 19+4 jobs; T5 NOT_RUN até o follow-up.

## 13. Ciclo e frescor (F5)

Lido docs/poc/oracle9_cycle_freshness.py e seu teste (não executados).
